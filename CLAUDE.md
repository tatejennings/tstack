# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

This repo *is* the **TStack** Claude Code plugin. It's not an application, it's not a documentation kit — it's a plugin you install into other projects so the TStack skills become available there: a six-stage chain (`discover → product → architect → roadmap → plan-milestone → build`), two iteration skills (`tstack-specify-feature`, `tstack-refactor`), one adoption on-ramp (`tstack-ingest`), a conditional UI design stage (`tstack-design`, runs product→design→architect for UI products), two optional off-chain companions (`tstack-status`, `tstack-wrap`), plus a manual-only autonomous runner (`tstack-autopilot`). The deliverable is the contents of `.claude-plugin/` and `skills/`.

Most edits here are editorial: tightening a `SKILL.md`, updating a `references/full-guide.md`, or refining the README. There is no build, test, or lint.

## Architecture

- `.claude-plugin/plugin.json` — plugin manifest (name, version, author). Skills are auto-discovered from `skills/`, not enumerated here.
- `skills/tstack-<stage>/SKILL.md` — the concise procedural top-level for each skill. Frontmatter `description` is load-bearing — it drives auto-triggering. ~120–200 lines max.
- `skills/tstack-<stage>/references/full-guide.md` — the long-form guide. Source of edge-case detail; SKILL.md tells Claude when to consult it. Each carries a header naming SKILL.md as the source of truth. The `discover`/`roadmap`/`build` guides are still the preserved pre-plugin prose; the `architect` and `product` guides have been actively maintained (de-staled/thickened) and are no longer verbatim.

The chain: `discover → product → architect → roadmap → plan-milestone → build`. Plus two **iteration skills** that re-enter the loop after launch and hand off to `plan-milestone`: `tstack-specify-feature` (add/change a feature) and `tstack-refactor` (restructure *how* the system is built with no product change — a superseding ADR + behavior-preserving milestones). Together with the backlogged `tstack-techdebt` (detects aged ADRs) and `tstack-retire` (removes a feature), they form an "evolve an existing project" family: **add / restructure / remove**. Neither iteration skill builds — both end by *recommending* `plan-milestone` (the recommend-and-stop property below).

**`tstack-ingest` is a chain on-ramp, not an off-chain skill.** It's an alternate entry point for projects that already have docs: it adopts the user's existing material and **hands off into the chain** (to `tstack-product`), the way `specify` hands off to `plan`. Because it has a required handoff, it is *not* off-chain. Don't reclassify it as off-chain, and don't fold its adoption logic into another skill — `tstack-discover` only *detects existing docs and forwards* to ingest; it never distills them itself.

**`tstack-design` is a conditional UI design stage with a retained off-chain mode — not an off-chain companion.** For products with a consumer-facing UI it runs **between `tstack-product` and `tstack-architect`** (so the frontend-stack ADR and ADR-3 come out design-informed): `tstack-product` *recommends* it for UI products and it *recommends* `tstack-architect`. Like `tstack-ingest` (an on-ramp, not off-chain), it has a place in the chain — but it **never blocks**, is **conditional** (skipped entirely for headless CLI/library/API products, which flow product → architect untouched), and stays **invokable at any point** (after roadmap, mid-build) for screen-level work. When editing it: don't make it mandatory (headless products must not see a design step) and don't strip its recommend-handoffs (that would regress it back to the old dead-end). It owns the `docs/3 - Design/` set and has two modes — *generate* (fidelity × route: a Claude Design brief, in-repo HTML previews, or a Figma round-trip) and *link-back* (record a brought-back Claude Design/Figma link/screenshots into the set).

Two skills sit **off-chain** (optional, invokable at any point, no required handoff): `tstack-status` (strictly read-only project inspector — reports status and doc drift, writes nothing) and `tstack-wrap` (end-of-session doc sweep — writes undocumented decisions/gotchas to the right doc, but never commits and never adds/renumbers milestones). When editing an off-chain skill, keep it off-chain — don't wire it into the linear flow; keep `tstack-status` from mutating anything, and keep `tstack-wrap` from committing or touching roadmap milestones.

**`tstack-autopilot` is the off-chain autonomous runner — invariants that must not regress.** It takes one milestone unattended to an *open PR* and is the only skill that runs without a human in the loop, so it carries hard rules (mirrors the loop invariants below): **(1) it never merges** — the run ends at an open PR for a human; **(2) it's manual-only** (`disable-model-invocation: true`) because it mutates git, and must never be made to auto-trigger; **(3) it's fail-closed** — it refuses unless the tree is clean/current, the M0/i0 baseline + CI exist, every "Done when" criterion is command-verifiable, deps are all Completed, and no `AGENTS.md`/`CONTRIBUTING` policy forbids autonomous pushes (consumer policy wins); never-merge is enforced by working on a feature branch and stopping at an open PR (a discipline rule — it does **not** require the consumer to enable GitHub branch protection, consistent with TStack never suggesting or requiring branch protection anywhere); **(4) the plan red-team replaces the human plan-approval gate, and quoted "Done when" output is the only authorizing gate** — self-review never authorizes; **(5) tests are append-only and it never chains** to the next milestone (PR-and-stop). It deliberately reuses *artifact contracts* (the `docs/plans/{id}-plan.md` schema, the quoted-verification format), not the `tstack-plan-milestone`/`tstack-build` skills themselves. It's markdown-only by decision (no `preflight.sh`/engine script); if you ever add one, update this note and the "no executable code" rule below.

**Cross-skill contracts (don't regress these when editing):**
- **`AGENTS.md` is owned by `tstack-architect`.** Only it writes the full file. `tstack-roadmap` and `tstack-build` update *only* the `## Current Focus` block; they never restructure the rest.
- **The approved plan is written in-repo at `docs/plans/{milestone-id}-plan.md`.** `tstack-plan-milestone` writes it; `tstack-build` reads it; `tstack-autopilot`'s handoff report sits beside it at `docs/plans/{milestone-id}-report.md`. It lives in the project (not a local user folder) on purpose: once committed (a manual step, left to the user), milestones can be planned ahead and built later by a cloud agent or a different machine. The schema lives in `tstack-plan-milestone/SKILL.md`.
- **`ROADMAP.md` has one full-regenerator (`tstack-roadmap`) and two append-only editors (`tstack-specify-feature`, `tstack-refactor`).** Roadmap carries a `Docs last synced:` marker; both editors advance it with a `(surgical: …)` annotation and never renumber existing milestones. A full re-sequence (including after a pivot) is roadmap's alone. `tstack-status` reads that marker to flag drift.
- **Iteration skills recommend-and-stop; they never auto-build.** `tstack-specify-feature` and `tstack-refactor` each end after writing docs + appending milestones, then *recommend* `tstack-plan-milestone` — they never start implementing and never invoke `tstack-build`. `tstack-plan-milestone` keeps its own fresh-session-before-build stop. Every arrow (spec → plan → build) is a human-gated recommendation, not an auto-chain — preserve this when editing.
- **`tstack-roadmap` validates "Done when" testability at write time** — every criterion must map to a runnable command before save, not be discovered as soft at build time.
- **`tstack-ingest` writes only to `docs/_adopted/` — never a canonical doc.** Adoption quarantines distilled material as an *unratified draft* (`docs/_adopted/PRODUCT.draft.md`, `docs/_adopted/*-notes.md`); nothing in `docs/_adopted/` satisfies any chain skill's prereq, so unverified content can't flow into the loop. The owning skill authors the canonical doc *from* the draft through its own gate — `tstack-product` reads `PRODUCT.draft.md`, authors `docs/PRODUCT.md`, and deletes the draft on save. During adoption, ingest also recognizes pre-existing **design material** (mockups, HTML with app design, style guides, token files) and stages `docs/_adopted/design.draft.md`, which `tstack-design` ratifies into the `docs/3 - Design/` set and deletes. Ingest never writes `PRODUCT.md`/`ARCHITECTURE.md`/`DECISIONS.md`/`ROADMAP.md`/`AGENTS.md`/the `docs/3 - Design/` set and never fabricates — it carries the source across and names what's missing in a visible `## Open gaps` block. This generalizes the old `tstack-discover` "distill existing material" branch (now removed; discover forwards to ingest). Don't let ingest write canonical files, and don't add a competing distill path elsewhere.
- **The `docs/3 - Design/` set is owned solely by `tstack-design`.** It writes `design.md` (UX + visual), `claude-design-prompts.md`, `design-tokens.json` (W3C DTCG), `previews/`, and `screens/{name}.md` at scale. `tstack-architect`, `tstack-roadmap`, and `tstack-build` **read** the set but never write it: architect lets it *inform* the frontend-stack ADR + ADR-3; roadmap attaches a `design.md — §screen` pointer to UI milestones; build verifies only the command-verifiable a11y slice (axe / contrast-from-tokens / keyboard) and never a soft "matches design". A brought-back design *link* skips `docs/_adopted/` and is recorded directly by `tstack-design` in a `## Design source` block; only a substantial pre-existing design corpus goes through ingest's quarantine (above).

**Foundational decisions live in `tstack-architect`.** Before generating any technical doc, the skill asks four mandatory questions (security, observability, accessibility, privacy) — each becomes an ADR in DECISIONS.md. Optionally a fifth question for AI/LLM products. DECISIONS.md and TESTING.md are now mandatory outputs at every right-sizing level. When editing `tstack-architect/SKILL.md`, preserve this order: prereq check → foundational ADRs → AI question → right-sizing → approach.

**`tstack-roadmap` mandates an `M0 — Infrastructure baseline` milestone** (CI, secrets, deployment skeleton, observability bootstrap, lint, test runner). The skill refuses to save a roadmap without it. Don't relax this when editing. **TStack never suggests or requires branch protection / required-review rules** — not in M0, not anywhere. It's the user's own repo-settings call; only honor it if the user records it themselves (in their planning, PRODUCT/DECISIONS docs, AGENTS.md, or CONTRIBUTING). Don't reintroduce it as a framework default.

## Design Invariants — the Agentic Loop

TStack is a harness for product-build loops. Three properties are what make the loop trustworthy over a long project; treat them as invariants and don't regress them when editing. (See the README's "The agentic loop" section for the user-facing version.)

- **Verification is the engine — keep it external and quoted.** `tstack-build` checks every "Done when" criterion by running a real command and pasting its output; `tstack-roadmap` refuses criteria that aren't command-verifiable at write time. Don't soften either — a self-asserted "✓" is not a signal.
- **State lives on disk, not in the session.** The docs + `docs/plans/{id}-plan.md` + ROADMAP's Status section are the loop's durable memory; that's why plans are in-repo and why `.tstack/state.json` was removed (see BACKLOG). Don't move cross-session coordination back into session memory.
- **Fresh session per milestone is the iteration boundary.** `tstack-plan-milestone` and `tstack-build` end and recommend a fresh session rather than auto-chaining (the v0.3.1 fix). Don't reintroduce same-window plan→build→next-milestone glide. Any future autonomous runner (BACKLOG #5) is opt-in re-automation *on top of* this default, not a reversal of it.

## Editorial Conventions (Match These When Editing)

- **Filenames use full words, no acronyms.** `PRODUCT.md`, not `PRD.md`.
- **Numbered doc-stage folders** organize the chain's outputs: `docs/1 - Discovery/` (discover), `docs/2 - Specs/` (architect breakout specs), `docs/3 - Design/` (design). Canonical root docs (PRODUCT.md, ARCHITECTURE.md, …) stay at `docs/`.
- **Every SKILL.md follows the same shape:** frontmatter → Prereq check → Approach → Reference handoff → Handoff. Don't break the symmetry — it makes the chain readable.
- **Frontmatter `description`** must lead with what the skill does, then "Use when…" triggers, then explicit Input/Output, then handoff. The Input clause is what makes Claude check prerequisites before triggering.
- **`tstack-product`, `tstack-specify-feature`, and `tstack-refactor` are mutually exclusive triggers.** Product creates the initial PRODUCT.md; specify-feature adds/changes a *feature* on an existing project; refactor changes *how* the system is built with no product change. Each description carries an explicit negative phrase routing to the other two (and refactor also routes a pivot back to `tstack-roadmap`). `tstack-design` is orthogonal to this trio — it defines *how it looks*, not *what to build*; its description carries a one-line negative route to `tstack-product`/`tstack-specify-feature`.
- **Verification in `tstack-build` requires quoted command output.** Every "Done when" criterion is checked by running a real command and pasting its output into the conversation. "Verified ✓" without output is not acceptable — match this discipline when editing the verification section.
- **AI-feature acceptance criteria use eval-based format**, not Given/When/Then. Required parts: eval set (versioned, on disk), quality bar (measurable threshold), fallback (deterministic). `tstack-product` enforces this — match the format when adding examples.
- **Always update `CHANGELOG.md`.** Any change to a skill's behaviour, a new/removed skill, or a manifest/README change adds an entry under the `## [Unreleased]` heading (Added / Changed / Fixed / Removed). This is part of every edit, not an afterthought. When tagging a release, move Unreleased entries under the new version heading and bump `version` in `.claude-plugin/plugin.json`.

## What NOT to Do

- Don't add a build system, tests, or CI — there's no executable code.
- Don't add `AGENTS.md` to this repo's root. The framework *produces* AGENTS.md in consumer projects, but the plugin itself isn't a consumer of itself.
- Don't enumerate skills in `plugin.json` unless plugin loading turns out to require it (currently it doesn't).
- Don't rewrite a `references/full-guide.md` unless asked — prefer editing the SKILL.md. The `discover`/`roadmap`/`build` guides remain preserved pre-plugin prose; keep them that way absent a request. (`architect` and `product` guides were intentionally reconciled against their SKILL.md — when you touch those, keep them consistent with the SKILL.md, which is the source of truth.)

## Common Tasks

- **Tweak a skill's behavior:** edit the relevant `skills/tstack-<name>/SKILL.md`. Keep it concise; move detail into the reference. Add a `CHANGELOG.md` Unreleased entry.
- **Update the auto-triggering of a skill:** edit only the `description:` field in the SKILL.md frontmatter. Test by saying the trigger phrases in a consumer project.
- **Add a new skill:** create `skills/tstack-<name>/SKILL.md` following the established shape. Update README's skill table and the skill-count wording in `plugin.json` / `marketplace.json`, and **regenerate the README lifecycle infographic with `/refresh-lifecycle`** (the diagram is now a generated image, not Mermaid — don't hand-edit `images/lifecycle.jpg`). Decide where it fits in the chain (or whether it's a parallel iteration skill like `tstack-specify-feature`, a conditional stage like `tstack-design`, or an optional off-chain companion like `tstack-status` / `tstack-wrap`). Add a `CHANGELOG.md` Unreleased entry.
- **Test the plugin:** see README's Quick Start. From a scratch directory, `/plugin install <this-repo-path>` and walk the chain.
- **Self-review the plugin:** run `/upkeep` (a repo-local skill at `.claude/skills/upkeep/`, *not* shipped — it lives outside `skills/` so the plugin loader never publishes it). It deep-reviews this repo for internal-consistency/sync drift, design-invariant or cross-skill-contract regressions, and currency against the live Claude ecosystem (model IDs/tiers, Claude Code features) and tech-stack major versions. Report-first; it auto-fixes only safe sync-point mismatches on approval. Reports land as dated files in `reviews/` (a diffable history; the first entry `reviews/upkeep-2026-05-30.md` is the original advisory review). Distinct from the planned consumer-facing `tstack-audit` (BACKLOG) — `/upkeep` audits the plugin's own source. Good to run before tagging a release.
- **Refresh the README lifecycle graphic:** run `/refresh-lifecycle` (a repo-local skill at `.claude/skills/refresh-lifecycle/`, not shipped). The lifecycle diagram and agentic-loop illustration are AI-generated images (Higgsfield `nano_banana_pro`), not Mermaid — so a chain change is a re-generate, not a redraw. The skill drift-checks the live `skills/tstack-*` set against the *Rendered graph* manifest in `images/BRANDING.md §11` and only regenerates when a node/role actually changed; it defers to `BRANDING.md §11` for the prompts/model/settings. Needs the Higgsfield MCP connected.
- **Cut a release:** say "ship" / "release" or run `/ship` (a repo-local skill at `.claude/skills/ship/`, not shipped). It runs the full procedure — version bump, CHANGELOG move + BACKLOG prune, branch→merge to `main`, annotated tag, and a `gh` GitHub Release with notes from the CHANGELOG section.
- **Track future work:** add to `BACKLOG.md` at the repo root. Solo-dev shorthand list of upcoming features, content gaps, and process items.
